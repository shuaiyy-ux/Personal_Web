构建实时 X/Twitter 狙击机器人：一段完整的 AI 辅助开发之旅（第一部分）

Shuaiyu Yao
UCI MSBA 26' | 全栈分析师
2025 年 10 月 16 日

我想写这个系列来记录我们从零开始构建 SniperBot 的完整过程，同时也想告诉大家，在当今这个时代，即使没有编程背景，借助 AI 的帮助也能做出令人印象深刻的项目。网上很多人只放一些代码片段，或者说一句"AI 很强大"，但很少有人完整地展示一个可复现的流程——这也是我写这个系列的原因之一。

起点

起点很直接。首先，Trump 刚刚发了他的币，价格疯狂波动，社交媒体上的情绪直接把价格推上了天；与此同时，大量 memecoin 在 Solana 上快速发行——一条推文或一个链接就能撬动市场。其次，GPT-4 刚刚发布，我们试用之后的感受是——说实话——非常惊艳。一个是市场窗口，一个是加速开发的工具。两者结合，我们当晚就做了决定：自己做一个狙击机器人。

问题

我们想解决的问题很明确：很多项目方或者有影响力的人发推时，会直接贴出合约地址，或者发一个项目页面链接，里面包含地址。如果我们能在两秒内捕获这些推文，而且这些推文来自高信号账户（例如发达国家的顶级政治人物、大品牌、核心 KOL），那么先发优势就非常重要——入场成本、滑点和执行价格会不同，回报可能天差地别。这种盯着高价值账户、一旦出现可交易标的就立刻行动的方式，在圈子里叫做"Sniper"（狙击）。

我们首先需要解决的问题：如何从 Twitter 获取信息

举个例子：如果 Trump 今天发了一条推文，推文中包含一个新的合约地址，或者链接到一个嵌有地址的项目页面——这正是我们想要第一时间捕获的推文。

只有当我们能够可靠且快速地捕获这类推文，后续的一切才有意义：提取文本、展开短链接、识别合约地址、验证真实性，然后把信号交给交易模块。

我们一开始基本没有网页开发经验：会写代码，但没建过网站；HTML/CSS 不熟；没用过自动化工具。这是我们的第一个完整项目；我们甚至没有路线图——就是直接开始，一步步推进。

第一次尝试：X/Twitter API —— 钱不是问题，没钱才是问题

简单来说，API 是网站或服务为开发者提供的一扇"门"；通过这扇门，你可以用程序请求数据或发送指令。对于 Twitter/X 来说，官方 API 可以让你查询推文详情、搜索匹配关键词的帖子，或者订阅特定的数据流（如果账户/权限允许的话）。优点是"官方 + 结构化"：格式固定，相对稳定，不需要解析混乱的网页。

一开始我们跟着教程，用 GPT 拼出了一个非常基础的 Python 脚本：拉取时间线并打印到控制台。配置好凭证后，二十分钟就拉到了第一条记录——感觉很棒。然后我们自然想让它持续运行、低延迟地监控几个高信号账户。现实打了我们一巴掌：速率/配额限制很快就阻断了"准实时"的目标，而要提高限额来持续监控，对于一个小型实验项目来说成本太高了。

价格明细

  • 免费版：用于测试/写入；读取能力非常低（月读取限额在几百到几千的量级——不足以持续监控）。
  • Basic（$200/月）：月读取量约 15k，应用/项目数量有限——对于我们所需的强度仍然不够。
  • Pro（$5,000/月）：用于早期扩展，官方示例配额约 100 万次读取/月，约 30 万次写入/月——支持更完整的搜索/流式能力。贵得离谱。

另外，许多端点有每 15 分钟窗口的速率限制。换句话说，如果你想按秒级监控几个时间线，允许的调用次数很快就会耗尽；队列和缓冲无法克服这个硬性限制。

总结：API 路线并非不可行，但要支持我们"准持续、小目标集、约 2 秒内检测"的使用场景，成本和可操作性都很差。所以我们切换到了更接近"人类浏览"的方式：让程序直接读取网页，而不是不断"调用 API"。

方案 B：自己搭爬虫

在此之前，先说说权衡：我们最初想用 Twitter API，因为它是官方的，看起来更干净、更稳定。爬网页并不是我们的首选——要么订阅别人的数据服务，要么面对反爬机制——阻力很大。但实际上，要以秒级延迟监控几个高信号账户并长期运行，API 的配额和成本把我们困住了。我们只能撸起袖子自己搭爬虫。我们选了一个浏览器自动化工具（Playwright），事情开始步入正轨。

核心思路：三个关键组件

1）运行一个"无窗口浏览器"，只读取新内容

我们在服务器上运行一个无窗口的浏览器（跟普通浏览器一样，但不显示在屏幕上）。它停留在我们想要监控的页面上；每当列表出现新帖子时，我们只读取那条新内容——不做全页刷新。更快、更安静，也更不容易引起问题。

2）利用 X Pro 的自动更新列

X Pro 有一个独立的界面，带有列表/列功能，可以自动推送新帖子——不需要全页刷新。列布局更稳定，不太容易意外变化；你可以同时打开多个列来监控多个账户/列表，减少切换。对于"快速检测 + 长期稳定"来说，这是理想的方案。

  • 你能立即看到新内容，这为后续的链接展开、文本清理和地址检查争取了时间；
  • 监控列表可以通过配置文件维护——换人只需修改配置，无需改代码；
  • 普通的首页时间线经常包含"自动刷新 + 推荐内容"，会混入无关的内容；X Pro 的列保持干净，只显示我们设置的列表，让我们能够专注。

3）登录一次，复用会话

我们手动登录一次，把会话保存到文件中。程序启动时加载这个文件——本质上就是机器人版的"记住我"。这样可以跳过登录表单，减少重复验证，更加稳定。

  1. 在普通浏览器中登录 X，确认你要监控的列；
  2. 将当前登录状态导出到一个小文件（即 cookies）；
  3. 启动时加载该文件，这样浏览器会话就已经是登录状态；
  4. 如果之后过期了，在计划的维护窗口期间刷新并更新该文件。

⚠️ 不要把你的 cookies 文件放到公开仓库里！

一个实用的经验分享：我是如何高效使用 AI 的

我的方法与敏捷开发高度一致——迭代、验证、修正。这里敏捷的本质不仅仅是写代码更快；而是把任务拆分成可验证的小单元，每完成一个功能就测试，然后再继续。这避免了写了几百行代码之后才发现根本性问题。

我使用 AI 的工作流是这样的：

  1. 清晰地定义目标——例如，"我想在两秒内捕获一条推文并提取合约地址。"
  2. 询问 AI 可能的方案以及需要的包/工具。
  3. 选择我能理解或部分了解的方案——例如，Playwright 和 HTML 解析是我能掌握的。
  4. 不盲目信任 AI——通过查看论坛、GitHub issues 或技术博客来验证方案的可行性。
  5. 方案确定后，让 AI 按清晰分隔的阶段帮忙写代码：获取 HTML -> 解包和结构化数据 -> 分析和定位内容 -> 提取和输出结果。每个阶段独立运行并验证后，再进入下一个阶段。

这样你验证的是每个模块，而不是事后一次性修复所有问题。AI 成为一个按需的技术伙伴：当某个组件失败或逻辑不对时，把那段代码粘贴给 AI，请它分析、重写或优化。这样可以保持整体方向正确，同时快速推进。

从某种意义上说，AI 赋予了独立开发者将敏捷实践应用于复杂项目的能力——不需要完整的团队，但你仍然可以频繁迭代、快速获得反馈并持续改进。
