AI Agent 架构深度解析：使用 Claude CLI 构建工具调用助手

本文记录了我们如何使用 Claude Code CLI 和 Python 构建一个流式、多轮对话、支持工具调用的 AI agent。我们将逐层剖析——从进程生成和事件流传输，到工具调用循环，再到上下文管理——最后给出从 CLI 迁移到 SDK 的具体路径。

1. 什么是 Agent？

在这个架构中，agent 不是一个独立的 AI 产品。它是一个中间程序，在用户浏览器和 Claude 之间架起桥梁。它的职责很简单：

  1. 从用户浏览器接收问题
  2. 通过 CLI subprocess 将问题发送给 Claude
  3. 如果 Claude 请求数据（例如"我需要查询数据库"），代替它执行该工具
  4. 将工具结果返回给 Claude
  5. Claude 继续推理并生成最终答案
  6. 将答案实时流式传输回前端

整个循环最多运行 6 次迭代（MAX_ITERATIONS = 6），以防止失控执行。

flowchart LR U["User (Browser)"] -->|HTTP request| S["server.py\nFastAPI + SSE"] S -->|invoke| A["agent.py\norchestrator"] A -->|stdin| C["Claude CLI\nsubprocess"] C -->|stdout JSON stream| A A <-->|execute / result| T["tools.py\ncustom tools"] A -->|SSE token events| S S -->|EventSource| U

为什么需要中间层？

Claude 本身无法执行代码、查询数据库或调用外部 API。Agent 以工具的形式提供这些能力，将 Claude 从一个文本生成器转变为一个能够收集信息、推理分析并给出有据答案的自主问题解决者。

2. Agent 如何启动 Claude

核心命令

Agent 使用 Python 的 subprocess.Popen 将 Claude CLI 作为子进程生成：

proc = subprocess.Popen(
    ["claude", "-p", "--model", "opus", "--output-format", "stream-json",
     "--verbose", "--include-partial-messages", "--no-session-persistence"],
    stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.PIPE,
    text=True, bufsize=1,
)

标志参数参考

标志 用途
-p 管道模式——禁用交互式界面；从 stdin 读取，写入 stdout
--model opus 选择 Opus 模型以获得最高能力
--output-format stream-json 输出按行分隔的 JSON 事件，便于结构化解析
--verbose 包含额外元数据（例如 token 用量）
--include-partial-messages 在每个 token 生成时即时输出（实现打字机效果）
--no-session-persistence 无状态模式；不将对话历史保存到磁盘

三个 I/O 管道

subprocess.Popen 在 agent 和 Claude CLI 之间建立了三个通信通道：

flowchart LR subgraph "agent.py (parent process)" WRITE["Write question"] READ["Read JSON stream"] ERRREAD["Read errors"] end subgraph "Claude CLI (child process)" STDIN["stdin"] STDOUT["stdout"] STDERR["stderr"] end WRITE -->|"pipe"| STDIN STDOUT -->|"pipe"| READ STDERR -->|"pipe"| ERRREAD
  • text=True——使用文本模式（UTF-8 字符串，而非原始字节）
  • bufsize=1——行缓冲 I/O（每次读写一行）

身份认证

命令中不包含任何 API 密钥或令牌。Claude CLI 使用本地 OAuth——首次运行时会打开浏览器窗口进行 Anthropic 账户登录。凭证存储在 ~/.claude/ 中，永远不会提交到代码仓库。

任何克隆此仓库的人都必须安装 Claude CLI 并使用自己的账户进行认证。

管道模式下的工具访问

在管道模式（-p）下，Claude 的内置工具（Read、Edit、Bash 等）被禁用。Claude 只能使用我们在 tools.py 中定义的自定义工具，它通过文本输出中的 XML 标签来调用这些工具。

3. 流式传输基础

非流式响应的问题

没有流式传输时，用户提交问题后只能盯着空白屏幕等待数秒，直到完整响应一次性到达。这会造成糟糕的用户体验，尤其是对于长篇回答。

流式传输的工作原理

使用流式传输后，token 在生成时即被输出——即我们熟悉的"打字机效果"：

Non-streaming:  Request --> wait 5s --> "The Dallas dealer received 3 cars, shipping $450"
Streaming:      Request --> 0.3s --> "The" --> "Dallas" --> "dealer" --> ... --> done

实时通信协议

协议 方向 类比 应用场景
HTTP request/response 单次 短信 标准 API 调用
SSE (Server-Sent Events) 服务器到客户端（单向） 直播 AI token 流式传输、推送通知
WebSocket 双向 电话通话 聊天室、协同编辑、游戏

本项目使用 SSE，因为我们只需要将 token 从服务器推送到浏览器。前端使用浏览器原生的 EventSource API 进行连接：

const es = new EventSource("/api/agent-stream?message=...");
es.onmessage = function(event) {
    const data = JSON.parse(event.data);
    // Append each token to the UI as it arrives
};

普通 HTTP 在一次响应后关闭连接。SSE 保持连接开启，让服务器持续推送事件，直到响应完成。

4. Claude CLI 的 stream-json 输出格式

不使用 stream-json 时

Claude CLI 向终端输出人类可读的纯文本：

The Dallas dealer received 3 cars, shipping $450.

使用 stream-json 时

相同内容变成按行分隔的 JSON 事件：

{"type":"stream_event","event":{"type":"content_block_delta","delta":{"type":"text_delta","text":"The Dallas"}}}
{"type":"stream_event","event":{"type":"content_block_delta","delta":{"type":"text_delta","text":" dealer received"}}}
{"type":"stream_event","event":{"type":"content_block_delta","delta":{"type":"text_delta","text":" 3 cars, shipping $450."}}}
{"type":"result","result":"The Dallas dealer received 3 cars, shipping $450.","total_cost_usd":0.03}

JSON 封装由 CLI 执行，而非 Claude 模型。无论输出格式如何，模型生成的 token 数量是相同的。

为什么 stream-json 很重要

如果没有结构化事件，你需要逐字符读取 stdout，而无法知道： - 响应何时完成（没有 result 事件） - 调用花费了多少（没有 total_cost_usd） - 一个逻辑事件在哪里结束，另一个在哪里开始

stream-json 提供了结构化的事件边界和元数据——这是构建可靠的 SSE 管道到前端的基础。

5. 流式事件系统

消息结构

一个 Claude 响应（消息）可以包含多个内容块，类似于一封包含段落和附件的电子邮件：

Message
+-- Content Block 0: text    "Let me query the data..."
+-- Content Block 1: tool_use query_data(code="df.head()")
+-- Content Block 2: text    "Based on the results..."

事件生命周期

流按照严格的时间顺序输出六种事件类型：

flowchart TB MS["1. message_start\n(message begins, input token count)"] --> CBS["2. content_block_start\n(block N begins -- text? tool_use? thinking?)"] CBS --> CBD["3. content_block_delta (x N)\n(incremental content fragments)"] CBD --> CBE["4. content_block_stop\n(block N complete)"] CBE --> |"repeat for\neach block"| CBS CBE --> MD["5. message_delta\n(stop_reason, output token count)"] MD --> ME["6. message_stop\n(message complete)"]

Delta 子类型

content_block_delta 事件携带一个 delta 对象，其 type 字段决定内容类型：

delta.type 内容 出现时机
text_delta 一段文本片段 Claude 正在生成文本响应
input_json_delta 一段工具参数 JSON 片段 Claude 正在调用工具（SDK 原生模式）
thinking_delta 一段推理过程片段 扩展思考已启用

嵌套结构

这些是嵌套关系，而非互斥选项。我们的代码逐层解包：

flowchart TB A["stream_event (CLI wrapper)"] --> B["content_block_delta (event type)"] B --> C["delta object"] C --> D["type: text_delta"] D --> E["text: 'Hello'"]

停止原因

message_delta 事件包含一个 stop_reason，告诉我们 Claude 为什么停止：

stop_reason 含义
end_turn Claude 自然地完成了响应
tool_use Claude 想要调用工具并等待结果
max_tokens 响应在 token 限制处被截断
stop_sequence 遇到了自定义的停止序列

6. 两层解析管道

原始 CLI 输出复杂且冗长。我们在向上层传递之前将其简化为三种事件类型。

第一层：_call_claude_stream()——翻译层

这个生成器函数从 stdout 读取 JSON 行并产出简化事件：

while True:
    line = proc.stdout.readline()       # Blocking read, one line at a time
    if not line:
        break                           # Empty string = process ended

    event = json.loads(line)            # Parse JSON string to Python dict
    etype = event.get("type", "")

    if etype == "stream_event":
        inner = event.get("event", {})
        if inner.get("type") == "content_block_delta":
            delta = inner.get("delta", {})
            if delta.get("type") == "text_delta":
                text = delta.get("text", "")
                if text:
                    full_text += text
                    yield {"type": "token", "text": text}

    elif etype == "result":
        cost = event.get("total_cost_usd", 0.0)
        yield {"type": "done", "text": full_text, "cost": cost}

第二层：run_agent_stream()——编排循环

消费简化事件并驱动工具调用循环：

for event in _call_claude_stream(messages, system_prompt):
    if event["type"] == "token":
        text += event["text"]              # Concatenate + forward to SSE
    elif event["type"] == "done":
        total_cost += event.get("cost", 0.0)
    elif event["type"] == "error":
        stream_error = event["error"]

简化事件总结

flowchart LR subgraph "Layer 1: _call_claude_stream()" RAW["Raw JSON lines\nfrom CLI stdout"] --> PARSE["Parse and\nsimplify"] end PARSE --> TOKEN["{type: 'token',\ntext: '...'}"] PARSE --> DONE["{type: 'done',\ncost: 0.03}"] PARSE --> ERR["{type: 'error',\nerror: '...'}"] subgraph "Layer 2: run_agent_stream()" TOKEN --> CONCAT["Concatenate tokens\ninto full_text"] DONE --> COST["Record cost"] CONCAT --> DECIDE{"Inspect full_text\nfor XML tags"} end
简化事件 来源 用途
token stream_event > content_block_delta > text_delta 将文本片段转发到前端
done result 事件 发出完成信号，记录费用
error CLI 进程失败 将错误暴露给调用方

7. 工具调用循环

在 Claude 完成响应流式传输后，累积的 full_text 会属于以下三种情况之一：

情况 1：存在 标签

Claude 有足够的信息直接回答：

3 cars were allocated to the Dallas dealer, shipping cost $450

Agent 使用正则表达式提取内容并返回给用户。循环结束。

情况 2：存在 标签

Claude 需要外部数据：

{"name": "query_data", "args": {"code": "df.head()"}}

Agent 解析 JSON，执行工具，并将结果回传：

tool_call = _parse_tool_call(text)             # Regex extract + json.loads
tool_name = tool_call.get("name", "unknown")   # "query_data"
tool_args = tool_call.get("args", {})          # {"code": "df.head()"}

tool_result = run_tool(tool_name, tool_args)   # Execute in tools.py

messages.append({"role": "assistant", "content": text})
messages.append({"role": "tool_result", "content": result_str})
# Continue loop -- call Claude again with updated messages

情况 3：纯文本（无标签）

Claude 以非结构化文本作为响应。将其作为最终答案返回。

完整循环流程图

flowchart TB START(["User submits question"]) --> INIT["Initialize messages list\nAppend system prompt + user message"] INIT --> CALL["Send messages to Claude CLI\nvia stdin pipe"] CALL --> STREAM["Stream response tokens\nConcatenate into full_text"] STREAM --> CHECK{"Inspect full_text"} CHECK -->|"contains "| EXTRACT_ANS["Extract answer via regex"] EXTRACT_ANS --> RETURN(["Return to user via SSE"]) CHECK -->|"contains "| EXTRACT_TOOL["Extract tool name + args\nvia regex + json.loads"] EXTRACT_TOOL --> EXEC["Execute tool in tools.py"] EXEC --> APPEND["Append to messages:\n1. assistant message (full_text)\n2. tool_result (JSON)"] APPEND --> GUARD{"iteration < 6?"} GUARD -->|"yes"| CALL GUARD -->|"no, max reached"| RETURN CHECK -->|"plain text"| RETURN

Token 截断不是问题

在流式传输过程中， 会以片段形式分布在多个 token 中到达：

token 1: ""
token 3: "{\"name\":"
token 4: "\"query_data\""
...
token N: "
"

这是无害的。Agent 在流式传输期间只是拼接文本。解析发生在流结束之后，此时 full_text 保证是完整的。

A->>C: system prompt + user question Note over C: Round 1 C-->>A: stream: "I need to query the data..." C-->>A: query_data(code="...") A->>T: run_tool("query_data", {code: "..."}) T-->>A: {"result": [{"vin":"V001","dealer":"Dallas"}, ...]} A->>A: Append assistant msg + tool result to messages Note over C: Round 2 A->>C: system prompt + full history C-->>A: stream: "Let me also check the constraints..." 8. 上下文管理

无状态的挑战

因为我们使用了 --no-session-persistence，Claude 在 subprocess 调用之间没有记忆。每次调用都是一张白纸——Claude 不知道前几轮发生了什么。

Agent 如何维护状态

Agent 在内存中维护一个 messages 列表，用于累积完整的对话记录：

# Initialization
messages = []
if history:                                         # Frontend chat history
    for h in history:
        messages.append({"role": h["role"], "content": h["content"]})
messages.append({"role": "user", "content": message})  # Current question

# After each tool round, append:
messages.append({"role": "assistant", "content": text})
messages.append({"role": "tool_result", "content": result_str})

构建输入文本

_build_input() 函数将整个 messages 列表序列化为一个纯文本字符串：

def _build_input(messages, system_prompt):
    parts = [system_prompt, ""]
    for msg in messages:
        role = msg["role"]
        content = msg["content"]
        if role == "user":
            parts.append(f"Human: {content}")
        elif role == "assistant":
            parts.append(f"Assistant: {content}")
        elif role == "tool_result":
            parts.append(f"Human: Tool result:\n{content}")
    parts.append("Assistant:")
    return "\n\n".join(parts)

Token 成本权衡

每次迭代都会重新发送完整的对话历史作为纯文本。Token 用量线性增长：

flowchart LR R1["Round 1\n~2,000 tokens\n(system prompt + question)"] --> R2["Round 2\n~4,000 tokens\n(+ round 1 history)"] R2 --> R3["Round 3\n~6,000 tokens\n(+ round 2 history)"] R3 --> R4["Round N\n~2,000 x N tokens"]

这是 CLI subprocess 方案的结构性限制。SDK 替代方案（在第 10 节讨论）通过仅发送增量消息来避免这种重复。

9. Claude 如何发现工具

没有魔法

Claude 没有任何内置机制在运行时"发现"工具。它只是阅读我们注入到系统提示中的文本描述。

工具规范

每个工具在 tools.py 中定义为一个 Python 字典：

QUERY_DATA_SPEC = {
    "name": "query_data",
    "description": "Execute a pandas expression against the loaded dataset...",
    "parameters": {
        "code": {
            "type": "string",
            "description": "Python/pandas code to execute.",
            "required": True,
        }
    },
}

从规范到提示

一个辅助函数将所有规范转换为人类可读的文本：

### query_data
Execute a pandas expression against the loaded dataset...
Parameters:
    - code: string (required) -- Python/pandas code to execute.

### run_allocation
Run the optimizer with given parameters.
Parameters:
    - n_vehicles: integer (optional) -- Number of vehicles to allocate
    - beta: float (optional) -- Revenue weight, default 0.7

这段文本被插入系统提示的 {tool_descriptions} 占位符中。Claude 阅读后理解有哪些可用工具，并在需要调用时以 XML 标签作出响应。

flowchart LR SPEC["tools.py\nSPEC dictionaries"] --> BUILD["_build_tool_descriptions()"] BUILD --> INJECT["System prompt\n{tool_descriptions} placeholder"] INJECT --> CLAUDE["Claude reads\nunderstands capabilities"] CLAUDE --> CALL["Responds with\n..."] CALL --> PARSE["Agent parses\nand executes"]

10. 端到端数据流

从 Claude 输出到 Claude 输入的完整转换链：

flowchart TB A["Claude CLI stdout\nLine-delimited JSON strings"] -->|"readline()"| B["json.loads(line)\nPython dictionary"] B -->|"extract text_delta\nfragments"| C["Concatenate into full_text\n(plain string)"] C -->|"regex match\n+ json.loads"| D["tool_call dict\n{name, args}"] D -->|"run_tool()"| E["tool_result dict\n{result, error}"] E -->|"json.dumps()"| F["result string\nappended to messages list"] F -->|"_build_input()"| G["Complete plain text\nfed to Claude CLI stdin"] G -->|"next iteration"| A

完整链路：从 stdout 获取 JSON 字符串 --> Python 字典（解包文本片段）--> 纯字符串（完整响应）--> Python 字典（解析工具调用）--> 执行工具 --> Python 字典（工具结果）--> JSON 字符串 --> 追加到 messages --> 拼接为纯文本 --> 通过 stdin 回传给 Claude。

11. CLI vs SDK：架构对比

当前架构（CLI + 文本解析）

flowchart LR U["User\n(Browser)"] --> F["FastAPI\n(SSE endpoint)"] F --> A["agent.py\n(orchestrator)"] A --> SUB["subprocess.Popen"] SUB --> CLI["Claude CLI\n(-p pipe mode)"] A <--> T["tools.py\n(custom tools)"] CLI -.->|"OAuth via\n~/.claude/"| AUTH["Local credentials"]

优势： - 无需管理 API 密钥；使用现有 CLI 登录 - 实现简单；易于理解和调试 - 对自定义工具定义有完全控制

劣势： - 每轮都重新发送完整对话历史（浪费 token） - 通过正则表达式解析 XML 标签中的工具调用（脆弱） - 需要在主机上安装 Claude CLI

SDK 迁移目标

flowchart LR U2["User\n(Browser)"] --> F2["FastAPI\n(SSE endpoint)"] F2 --> A2["agent.py\n(orchestrator)"] A2 --> SDK["Anthropic SDK\n(Python client)"] SDK --> API["Anthropic API\n(cloud endpoint)"] A2 <--> T2["tools.py\n(custom tools)"] SDK -.->|"API key\nsk-ant-xxx"| KEY["Environment\nvariable"]

逐项对比

维度 CLI + 文本解析 SDK 原生工具
工具发现 系统提示中的文本描述 通过 tools 参数传递结构化 JSON Schema
工具调用 文本输出中的 XML 标签 tool_use 内容块（结构化）
参数格式 Claude 自行生成 JSON 字符串 API 保证符合 schema 的 JSON
可靠性 正则解析；Claude 可能生成格式错误的 JSON 格式由 API 契约保证
解析方式 手动正则提取 + json.loads SDK 直接返回 Python 对象
Token 效率 工具规范消耗 prompt token；每轮重发完整历史 专用 tools 字段；增量消息
身份认证 OAuth 浏览器登录 API 密钥（sk-ant-xxx）
计费方式 订阅方案（Pro/Max） 按 token 用量付费
部署方式 需要在主机上安装 CLI 仅需 pip install

迁移范围

从 CLI 到 SDK 的迁移是有针对性的——大部分代码无需改动：

组件 所需变更
_call_claude_stream() 用 client.messages.stream() 替换 subprocess
_build_input() 用 JSON 消息数组替换纯文本拼接
工具 SPEC 字典 转换为 input_schema（标准 JSON Schema）格式
工具执行逻辑 无需变更
SSE 推送到前端 无需变更
前端代码 无需变更

预期收益

  • Token 成本降低 20--30%——不再重复发送历史；工具规范在专用字段中
  • 工具调用格式有保证——不再出现正则解析失败或 JSON 格式错误
  • 更简单的部署——不依赖 CLI 安装；只需 pip install anthropic
  • 增量消息——每轮只发送新消息，而非完整历史

未来：Agent SDK

更长远来看，Claude Agent SDK 可以自动封装整个工具循环：

flowchart LR U3["User"] --> F3["FastAPI\n(SSE)"] F3 --> ASDK["Agent SDK\nautomatic tool loop"] ASDK --> API3["Anthropic API"] ASDK <--> T3["tools.py"]

Agent SDK 消除了手动的 while 循环、迭代保护和工具调用解析。但它仍在成熟中。先迁移到标准 SDK 是更安全、更可预测的中间步骤。

总结

这个架构展示了构建 AI agent 的一种实用模式：使用 LLM 作为推理核心，通过自定义工具扩展其能力，并通过流式中间层编排交互。基于 CLI 的方案简单有效，适合原型开发，同时也存在清晰的 SDK 迁移路径，满足生产环境对可靠性和成本效率的要求。
