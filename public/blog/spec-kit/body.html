Summary

How to iterate SpecKit work with plans, tasks, and tests-first loops while keeping every change traceable.

  • Rerun /speckit.plan only when strategy or requirements change; otherwise adjust tasks.md.
  • Practice TDD: write tests, see them fail, then add the smallest implementation to go green.
  • Keep contracts and code aligned by updating spec.md, plan.md, and tasks.md together.
  • Capture real test outputs (local or CI) as evidence for each iteration.

SpecKit Commands

  • /speckit.constitution — Define governing principles and development guidelines.
  • /speckit.specify — Describe what to build (requirements and user stories).
  • /speckit.plan — Create technical plans with your chosen stack.
  • /speckit.tasks — Generate actionable implementation tasks.
  • /speckit.implement — Execute tasks according to the plan.

Core Concepts

When to Rerun /speckit.plan

  • Requirement changes or original plan is infeasible: rerun /speckit.plan to rewrite plan.md with a new strategy.
  • Only implementation details shift: skip /speckit.plan; adjust tasks.md or code directly.
  • Already implementing: plans are set; refine tasks, not the plan generator.

One-liner: /speckit.plan answers "how to do this," not "how to write this line of code."

Test-Driven Development (TDD)

TDD requires real failing tests before writing core logic. Do not code from intuition; code to satisfy failing tests.

  1. Write the test for the expected behavior.
  2. Run it and confirm it fails (proves the test is meaningful).
  3. Write the minimum implementation to make it pass.
  4. Refactor safely under test coverage.

Why emphasize "tests are failing": ensures coverage of target behavior, avoids self-validation where implementation comes first, and uses tests to constrain boundaries and correctness.

AI + SpecKit + TDD

LLMs compress the red-green loop unless you force evidence. Use these safeguards:

  • Split tasks: keep "write tests" separate from "implement".
  • Demand evidence: capture failing and passing outputs.
  • Let local or CI test execution drive: use real results as next-round input.

Local Iteration Workflow

flowchart TD A[Change Request in spec.md] --> B[Update tasks.md Incrementally] B --> C[Write Tests Only] C --> D[Run Tests Locally] D --> E{Fail as Expected?} E -- No --> C E -- Yes --> F[Minimal Implementation] F --> G[Run Tests Again] G --> H{All Pass?} H -- No --> F H -- Yes --> I[Optional Refactor] I --> J[Record Change and Merge]

Step 1: Update spec.md with a Change Request

Add a "Change Request" or "Update" section containing:

  • Background: why this change exists.
  • Expected behavior: location and defaults.
  • Interaction: click/keyboard behavior, navigation, API calls.
  • Acceptance: observable, testable criteria.

Example Change Request

  • Change: Home Page adds a "Get Started" button.
  • Position: Below the main title, centered.
  • Behavior: Click navigates to /signup.
  • Accessibility: Button must be keyboard-focusable and triggerable with Enter.
  • Acceptance: Button visible on Home page; URL becomes /signup on click; layout does not overflow on mobile.

Step 2: Generate Tasks

  1. Update spec.md with the change.
  2. Run /speckit.tasks to generate incremental tasks.
  3. Prefer tests-first ordering inside tasks.md.

Step 3: Tests-First Execution

  • Task 1: Add tests for the new behavior.
  • Task 2: Run tests and capture failing output.
  • Task 3: Implement the minimal change to pass.
  • Task 4: Run tests again; refactor if green.

State new test files and commands explicitly. Document expected failure points before implementation. After failing output, modify only implementation unless tests are wrong.

Large-Feature Iteration

flowchart TD A[Large Feature Defined] --> B[Split into Milestones] B --> C[Milestone 1] C --> D[Milestone 2] D --> E[Milestone 3] E --> F[Feature Complete]

Each iteration should deliver a verifiable vertical slice:

  • Contract change recorded in spec.md.
  • Strategy and gates in plan.md.
  • Ordered tasks in tasks.md with tests-first.
  • Code plus tests committed to the repo.
  • Real test output (local or CI) feeds the next round.

Core principle: iterate on files and test outputs, not on chat impressions.

Per-Milestone TDD Loop

flowchart TD A[Milestone Spec Update] --> B[Tasks for Milestone] B --> C[Write Tests Only] C --> D[Run Tests Locally or CI] D --> E{Fail as Expected?} E -- No --> C E -- Yes --> F[Implement Minimum Scope] F --> G[Run Tests Again] G --> H{Pass Gates?} H -- No --> F H -- Yes --> I[Record Evidence]

Milestone Slicing Example (Signup Feature)

  1. Page opens with form; front-end validation works; submit is stubbed.
  2. Wire the API contract; simulate success; navigate on success.
  3. Handle failure states and error UI.
  4. Add e2e coverage and CI gates.
  5. Refactor and pay down debt.

Traceability

  • spec.md: revision log of contracts (add Change Log or Revision section).
  • tasks.md: milestones with acceptance points.
  • Git: each milestone mapped to PRs or commits named for the milestone.

At any point you can answer: current milestone, affected contracts, test coverage status, failure outputs, and fix paths.

Prompt Templates

Template 1: Generate or Update Plan

"Based on the latest spec, output a plan for feature X including phases, risks, test strategy, and gates. Do not write implementation code."

Template 2: Generate Tasks

"Based on the plan, split work into milestones. Each milestone must include tests-first task ordering and specify new test file paths and run commands."

Template 3: Tests Only

"Complete only Milestone N's test tasks. Only modify the tests directory, not src. Output test files, commands, and expected failure points."

Template 4: Minimal Implementation

"Here is my local test failure output. Only modify implementation to pass these tests. Do not modify tests unless they are demonstrably wrong."
