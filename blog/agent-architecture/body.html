Agent internals, streaming, tool loops & migration paths

This post walks through how we built a streaming, multi-turn, tool-calling AI agent on top of Claude Code CLI and Python. We'll peel back every layer — from process spawning and streaming events, through the tool-call loop, to context management — and finish with a comparison of CLI vs SDK approaches.

1. What Is the Agent?

The agent is not a standalone AI product — it's a middleman program that sits between the user's browser and Claude. Its job is simple: receive a question, feed it to Claude, execute any tools Claude requests, return results, and repeat — up to 6 iterations to prevent runaway loops.

2. How the Agent Starts Claude

A single subprocess.Popen call boots Claude CLI as a child process with three I/O pipes:

flowchart LR Agent["agent.py"] -->|"stdin (question)"| CLI["Claude CLI"] CLI -->|"stdout (JSON stream)"| Agent CLI -->|"stderr (errors)"| Agent
FlagPurpose
-pPipe mode — no interactive UI; reads stdin, writes stdout
--output-format stream-jsonLine-delimited JSON events for structured parsing
--include-partial-messagesEmit every token immediately (typewriter effect)
--no-session-persistenceStateless — each call is a fresh conversation

Auth: Claude CLI uses local OAuth (browser login stored in ~/.claude/). No API key is needed — but anyone who clones the repo must log in with their own account.

Tool access: In pipe mode, Claude's built-in tools (Read, Edit, Bash) are disabled. The only tools available are the ones we define in tools.py, invoked via XML tags.

3. Streaming Fundamentals

Without streaming, the user stares at a blank screen for seconds until the full response lands. With streaming, tokens arrive in real time — the familiar "typewriter effect."

TransportDirectionAnalogyUse Case

We use SSE (Server-Sent Events) because we only need one-way push from server to browser. The frontend connects with a native EventSource object.

4. Claude's Streaming Event System

A single Claude response can contain multiple content blocks — text, tool calls, or thinking traces. The event lifecycle follows a strict nesting:

(block 0: text)"] CBS1 --> CBD1["content_block_delta × N
(text tokens)"] CBD1 --> CBE1["content_block_stop"] CBE1 --> CBS2["content_block_start
(block 1: tool_use)"] CBS2 --> CBD2["content_block_delta × N
(JSON fragments)"] CBD2 --> CBE2["content_block_stop"] CBE2 --> MD["message_delta
(stop_reason, usage)"] MD --> ME["message_stop"]

Our code only cares about two things from this stream:

  • content_block_delta with text_delta — the actual text tokens to display
  • result — the final summary with cost info

The delta subtypes determine what kind of content is arriving:

6. The Tool-Call Loop

After Claude finishes a response, the full text falls into one of three buckets:

  • <answer> tag — extract and return the final answer
  • <tool_call> tag — parse tool name + args, execute, feed result back to Claude
  • Plain text — treat as the final answer
flowchart TB START(["User question"]) --> CALL["Send to Claude"] CALL --> STREAM["Stream response → full_text"] STREAM --> CHECK{"Inspect full_text"} CHECK -->|"<answer> found"| RETURN(["Return answer to user"]) CHECK -->|"<tool_call> found"| EXEC["Regex extract → json.loads
→ run_tool()"] CHECK -->|"plain text"| RETURN EXEC --> APPEND["Append assistant msg
+ tool result to messages"] APPEND --> GUARD{"iteration < 6?"} GUARD -->|yes| CALL GUARD -->|no| RETURN

Token truncation isn't an issue: during streaming, we only concatenate text. Parsing happens after the stream ends, so <tool_call> is always complete.

7. Context Management

Because we use --no-session-persistence, Claude has no memory between calls. The program maintains a messages list and rebuilds the full conversation each time:

sequenceDiagram participant U as User participant A as Agent participant C as Claude U->>A: "How many cars went to Dallas?" A->>C: system prompt + user question C-->>A: <tool_call>query_data(...)</tool_call> A->>A: Execute tool, append to messages A->>C: system prompt + full history + tool result C-->>A: <answer>3 cars, shipping $450</answer> A->>U: Final answer

Trade-off: every iteration resends the entire conversation history as plain text. Token usage grows linearly — round 1 costs ~2K tokens, round 2 ~4K, round 3 ~6K. This is a structural limitation of the CLI subprocess approach.

8. How Claude Discovers Tools

There's no magic. Each tool has a SPEC dict in tools.py. A helper function converts all specs into human-readable text and injects it into the system prompt. Claude reads the spec, understands what's available, and responds with XML tags when it wants to invoke a tool.

In short: JSON string → Python dict (unpack text) → string → dict (parse tool call) → execute → dict → string → concatenate into plain text → feed to Claude.

Migration is Minimal

  • Replace _call_claude_stream() — swap subprocess for SDK client
  • Replace _build_input() — plain text concatenation → JSON message array
  • Convert tool SPEC dicts to input_schema format
  • Everything else (tool execution, SSE push, frontend) stays the same

Expected Gains

  • 20–30% token savings — no repeated history resend
  • Guaranteed tool-call format — no more regex parsing failures
  • Simpler deployment — no CLI installation dependency

Looking further ahead: the Claude Agent SDK wraps the entire tool loop automatically — no manual while loop needed. But the SDK is still maturing; migrating to the standard SDK first is the safer intermediate step.
